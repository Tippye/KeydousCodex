# Keydous Codex Bridge 设计与能力边界

当前状态：Windows 0.3.2 提供独立 WebView2 桌面窗口、Codex Hook 状态、可选 RGB 联动、旋钮快捷操作和手动屏幕上传，具体证据见 [验收记录](docs/acceptance.md)。项目 fork 自 Keyphore，复用官方 Keydous IoT 驱动；macOS 适配仍为实验性源码。

**Keydous NJ98 的图像／动画上传耗时，刷新速度不适合频繁更新，因此当前不能实现键盘屏幕与 Codex 状态实时同步。** 已上传动画可播放，状态标签与状态栏仅为生成时刻的快照。原生状态层、低成本动态切页和实时画面接口均未验证；不以每次事件重传 GIF 的方式实现同步。RGB 和旋钮不受这一屏幕能力限制。

下文保留早期方案比较与研究证据，未验证路径不代表当前功能或交付承诺。

后续用户指定基于 [Keyphore](https://github.com/BarryBarrywu/Keyphore) 实现。以提交 `9ca11f275809ebc2649bf365effdee8cc7682084` 为基线，将 Windows/Keydous 实现放在其 `windows/` 目录；复用八类 Hook 与持久状态核心的语义，替代日志输入作为推荐状态来源。原有日志输入保留为明确选定文件的辅助模式。平台差异记录在 `../docs/adr/0009-add-windows-keydous-port.md`。

## 目标与优先级

当前支持 NJ98 USB 有线连接。Codex 动态状态由桌面界面及可选 RGB 灯光表达，旋钮用于快捷操作。宠物、Num/Caps、连接与电量组合为可预览、导出和手动上传的画面；这些信息不会在键盘屏幕上自行更新。保留固件原生状态层与实时宠物状态显示属于早期探索，当前未实现。

其他型号按协议族和已验证能力扩展；不把所有名称包含 NJ98 的设备视为同一种硬件，不承诺未测试型号可写入。

## 已取得的证据

1. 项目起始快照（TaskStartSnapshot）：当前目录为空，无项目代码、AGENTS.md 或 Git 元数据；未创建分支。调查没有修改键盘配置、图片、固件或 IoT 安装目录。
2. `C:\Program Files (x86)\iot_driver\iot_driver.exe` 正在运行，监听 `127.0.0.1:3814`。
3. 官方网页实际引用 `static/js/main_d787f8ef.js`。该脚本的客户端使用 HTTP gRPC-Web / Protocol Buffers 访问本地 IoT 驱动，不能沿用前序讨论中 WebSocket 的猜测。
4. 对官方客户端使用的 `watchDevList` 发起只读订阅，收到 HTTP 200 和设备列表：VID 12625（0x3151）、PID 16405（0x4015）、设备 ID 1021、online=true。匹配官方设备配置 `yc500_nj98_soc` / NJ98。另有一个同 VID/PID 的原始 HID 类型条目，不应当作第二把键盘。
5. 该配置引用的屏幕能力为 `kbW:160, kbH:80, isRgb:"16"`。这是彩色图像传输格式；与按键背光 RGB 是两个独立功能。
6. 设备消息定义含 battery、is24、isonline 等字段；本次 NJ98 返回没有 battery 字段。Protobuf 缺省值不能证明实际电量是 0%。当前匹配有线设备配置，不能据此推导蓝牙槽号。
7. NJ98 屏幕传输使用分块像素数据，准备阶段含 left/top/right/bottom 坐标。这证明传输描述有矩形范围，尚不能证明默认界面允许替换黑猫、保留状态覆盖层，或允许在 RAM 中实时刷新。
8. 官方型号表同时存在 NJ98、NJ98-V2、NJ98-CP 等不同配置和协议族。型号名称不足以选择协议。

## 方案选择

| 路径 | 优点 | 限制 | 决策 |
| --- | --- | --- | --- |
| 原生状态界面 + 替换宠物区域 | 锁定、连接、电量由固件维护，离开电脑仍可显示 | 局部替换、默认猫资源是否开放尚待实机验证 | 未实现的研究路径 |
| 自定义全屏合成宠物 + 状态栏 | 布局可控，可增加 Codex 状态标签 | 当前上传接口不适合频繁更新 | 已实现手动快照／动画上传，无实时同步 |
| 上传宠物动画，保留原生状态页供切换 | 可通过官方图片上传流程交付基本显示 | 没有验证到软件自动切页接口 | 不承诺随 Codex 状态切页 |

自定义合成的建议布局（160×80）：顶部约 12 像素显示 Num/Caps、连接和电量；中间约 56 像素放宠物；底部约 12 像素显示 IDLE / THINK / WORK / WAIT / DONE / ERROR。实际边界以原生界面和宠物裁剪效果为准。

## 最小实现结构

一个 Windows 本地桥接程序，内部划分四个职责，初期不拆成多个服务或独立包：

- **Codex 状态输入**：归一化 idle / thinking / working / waiting / success / error。优先针对用户实际使用的 Codex 桌面端验证数据来源；CLI JSONL 是独立输入，不能声称它能观察现有桌面任务。多任务情况下优先跟随用户指定任务，避免任意扫描历史内容。
- **宠物与场景渲染**：读取经过验证的宠物 manifest 和 spritesheet 格式，裁剪、缩放、处理背景，输出设备尺寸的预览和导出资源。不能直接将前序对话中假定的 spritesheet 布局当作已确认格式。
- **设备能力配置**：用协议族、VID/PID、内部设备 ID 和必要的固件版本选择屏幕尺寸、色彩格式、上传模式、状态能力。未知设备保持只读。
- **IoT 设备输出**：复用现有本地驱动，负责设备发现、重连和串行传输。屏幕显示与按键 RGB 分开控制，避免把显示标签变成新的全局状态机。

状态数据必须附带来源和有效性：Num/Caps 可在本机读取，但它们表示当前 Windows 主机状态；连接与电量优先取设备真实遥测。未取得 BT 槽号显示 BT，不猜 BT1；未取得电量显示未知或隐藏。设备不再连接本机时，电脑状态不能继续冒充键盘状态。

## 更新与存储边界

先确认上传命令写入 Flash 还是 RAM，再决定刷新方式。持久化图片只在用户更新资源时上传。只有验证固件支持低成本的软件切页，才能使用预加载动画随 Codex 状态切换；当前没有证据证明这种切页命令存在。

不能在每次 Codex 事件、锁定变化或电量变化时重写 GIF。若没有适合动态刷新的接口，全屏合成不作为实时状态方案。

RGB 输出默认关闭；启用后复用同一 Codex 状态，提供独立输出配置。正常退出恢复原设置；异常退出的恢复能力需验证，不能承诺进程崩溃时必定恢复。

## 实施顺序与验收

1. **确认硬件显示能力**：核对当前屏幕/固件版本与可恢复的设置，验证自定义内容是否能与原生状态层共存，以及矩形范围的实际含义。验收证据必须包括实机显示，单纯接口返回成功不够。
2. **宠物预览和导出**：确认本机宠物来源与格式；制作 160×80 预览和官方驱动可导入资源。验证尺寸、帧数、颜色、透明背景与裁剪。
3. **NJ98 接入**：实现只读发现、能力识别、数据有效性和经过验证的屏幕输出。设备断开后停止更新，重连后重新识别。
4. **Codex 联动**：分别验证桌面端和 CLI 输入支持范围。只有可观测的状态才能映射；结束状态可短暂展示后回到 idle。
5. **扩展型号**：复用渲染和状态输入，通过协议适配器扩展。每个型号记录“已识别 / 可导出 / 已实机上传 / 已验证动态状态”等独立证据。

关键验收场景：Num Lock 切换、USB/2.4G/BT1–3 切换、充电/电量缺失、Codex 工作/等待/完成/失败、并发任务、IoT 服务停止、拔线重连。只有真实数据可用的连接模式才宣称支持状态同步。

## 当前未解决项与续接点

- 原生猫是否可替换，以及用户图片是否保留状态覆盖层。
- 图像接口的持久化行为；软件切页或实时刷新是否受支持。
- 蓝牙槽号和有线电量是否有可用读取接口。
- Codex Hook 接入、宠物导入和渲染已实现；用户真实配置中的 Hook 启用须通过程序内的审阅界面完成。隔离配置的真实生命周期已验证。
- Windows 可运行程序与发布包已生成。用户已目视确认 work 动画显示；其他状态和自动切页未验收。后续屏幕写入仍需用户选择可覆盖槽位；不能把预览、协议测试或 ACK 当作屏幕实机验收。

## 新增范围：同一程序的双平台改键（用户已批准）

2026-09-06 用户批准“同一应用 + 内部虚拟 HID 组件”，并要求 Windows/Web 尽量保持 Keyphore 原版 UI 和使用方式。UI 以原版 KeyphorePopover、SignalSettingsView、DiagnosticsView 和 GuidedSetupView 的状态首页、设置分组和引导顺序为依据；保留 Keydous 专属宠物/屏幕/改键能力，不伪造 NuPhy 能力。Web 与 Windows 入口使用同一界面。

### 产品形态与边界

保持一个 Keydous Codex 应用、一个设置界面和一份用户配置。屏幕、宠物、RGB、键盘普通层/Fn 层改键在此管理。Windows 与 macOS 共用状态、渲染、协议、配置校验和界面；各平台只提供必要的启动、权限、输入和打包实现。原有 Keyphore macOS/NuPhy 工程不成为第二个 Keydous 产品，也不作为 Keydous Mac 支持已经完成的证据。

“同一个程序”按一个安装入口和统一生命周期实现；macOS 的原生 Fn/Globe 需要应用管理的特权辅助组件和虚拟 HID 系统扩展，无法合理承诺所有功能都在单个无权限进程中运行。用户无需另行配置 Karabiner-Elements 主程序。

### 方案比较与建议

| 路径 | 能力与代价 | 结论 |
| --- | --- | --- |
| 仅 NJ98 固件改键 | 普通层、固件 Fn 层可共用两平台协议；不能证明生成 Apple Fn/Globe | 作为两平台共同能力，不能单独满足 Mac Fn 要求 |
| 固件改键 + Quartz 软件映射 | 可处理普通按键和系统可见的 Fn；不能完整生成 Globe 行为，也不能按键盘区分来源 | 不作为完整 Mac Fn 的替代实现 |
| 固件改键 + 集成虚拟 HID | 具备实现原生 Fn/Globe 和按设备输入处理的基础；需签名、系统扩展授权及特权组件 | 推荐，符合完整 Mac Fn 与同一应用的要求 |

优先评估复用 Karabiner 已签名的 VirtualHIDDevice 组件及其客户端协议，保持原有签名与许可；我们的受限辅助组件管理输入与规则。不能随意改名后沿用签名，也不能把上游开发者权限视为我们自己的权限。自行构建和分发修改过的系统扩展需要相应 Apple entitlement。发布前核实组件许可、签名、版本一致性与安装/卸载兼容性；不可静默移除其他软件共用的上游驱动。

### 两种 Fn 的用户行为

- **键盘 Fn 层**：NJ98 固件动作，按键及旋钮可配置。普通层和 Fn 层各一个已知 bank。保留未知槽位和原始动作，不推测隐藏 Mac bank。
- **macOS Fn/Globe**：主机输入动作，可把能被主机收到的按键映射为 Fn/Globe。NJ98 实体 Fn 可能完全在固件内部处理；在实机证明可见之前，界面不承诺捕获它。Windows 不暴露虚构的原生 Fn 键码。

界面在同一“按键映射”页区分“写入键盘”和“本机 macOS 行为”。保存草稿不触发固件写入或自动开启主机拦截。规则按能力验证；不支持的规则明确显示未启用。

### 设备操作与恢复

NJ98 精确身份沿用现有 allowlist，普通层 0x89 / Fn 层 0x90 读取八个完整 64 字节块。单键写入分别为 0x13 / 0x15，使用真实矩阵 slot。依据见 `docs/nj98-mapping-research.md`；目前为源码证据，未通过实机改键验收。

每次应用改键前保存两层原始矩阵、设备身份及校验值。只写修改过的单键，随后重读整层，验证目标变化与所有未改槽位。失败中止并保留恢复记录；恢复也使用已验证单键路径，不使用不能覆盖完整矩阵的 bulk 命令。断开重连重新验证身份和当前值，避免用过期草稿覆盖其他修改。改键和屏幕/RGB 复用现有串行设备访问所有者。

### macOS 生命周期与权限

主应用及网页服务保持普通用户权限。仅原生辅助组件持有必要输入权限，IPC 验证调用者身份并接受经过验证的映射配置，不提供任意命令执行。输入事件不写日志、不送网络、不暴露给网页。权限未授予、被撤销或辅助组件退出时，界面标记映射未运行；释放已生成的按键并停止设备独占，避免卡键或吞键。重载规则须保持按下/释放配对和多键共享修饰键计数。

macOS 的输入监控、后台组件和系统扩展授权由程序内“启用 Mac Fn”引导。安装、停用、升级和卸载入口也在同一应用内。已有 Karabiner 或其他 remapper 时检测冲突并明确报告，不能同时抢占同一设备。官方提供 Mac 驱动，但本机尚无证据证明其 IoT 服务接口与当前 Windows 服务完全一致；Mac 硬件访问须先验证发现、只读协议及恢复，再开放写入。

### 顺序、验收与外部条件

1. 在现有 Windows 程序完成 NJ98 固件改键、备份恢复和同一界面，保持现有宠物、Hook、RGB 测试通过。先只读核实实机矩阵，再进行可恢复的单键验收。
2. 完成屏幕实机上传与观察，确认自定义画面能否保留原生状态栏。缺少动态页切换/易失性接口时，不以频繁写 GIF 实现状态联动。
3. 提取实际平台差异，生成同一应用的 macOS 构建；不复制整套业务。验证 Mac IoT 服务和 USB NJ98，USB/2.4G/蓝牙分别记录能力。
4. 集成 Mac 虚拟 HID 和 Fn/Globe。验证 Fn 单击、组合、先释放 Fn、重复、多键、左右修饰键、系统 F 键偏好两种设置、睡眠唤醒、拔线、权限撤销、重启、停用卸载和第三方输入工具冲突。
5. Windows 回归及发布包验收后，在真实 Mac 上构建、签名和运行验收。模拟测试不能代替 macOS 系统授权、Globe 系统动作和实机效果；没有 Mac 环境时只报告源码/模拟验证，不标为双平台测试通过。

外部条件：新的屏幕覆盖试验仍需明确槽位；已有 work 动画用户观察记录见 acceptance.md。Mac 的系统版本、芯片类型、运行条件尚待回复。上游的 macOS 支持声明不是本程序已通过的测试。

设计评审结论：复用现有应用所有者；新增原生输入组件的必要性来自 Quartz 的已知限制。用户已批准特权输入组件及其安装生命周期，ADR-0009 已同步。Windows 改键和 UI 已实现；普通层/Fn 层实机单键读写及恢复已通过。Mac 源码与打包入口实施中，尚无真实 Mac 构建和输入效果证据。
